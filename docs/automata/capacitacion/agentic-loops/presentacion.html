Agentic Loops

Cómo encadenar sesiones de IA para que el código se construya solo — de forma autónoma, segura y controlada.

1¿Qué es un agentic loop?

Un sistema donde una sesión de IA termina y dispara automáticamente la siguiente, formando un ciclo autónomo de trabajo sin intervención humana.

Supervisor
project-manager
Decide qué issue sigue
→
Operario
complete-issue #N
TDD + commit + cierre
↺
Supervisor
project-manager
¿Más issues? Decide

El supervisor no ejecuta. El operario no decide. Ninguno te necesita entre turno y turno.

Cuándo tiene sentido

✓ Buen caso de uso

  • Tareas predecibles y bien definidas (issues con checklist)
  • Estado verificable externamente (GitHub, archivos, tests)
  • Errores recuperables — no afectan producción crítica
  • Tenés guardrails para detectar cuando algo sale mal

✗ Mal caso de uso

  • Tareas que requieren decisiones ambiguas frecuentes
  • El costo de un error es muy alto
  • No hay tests automatizados que validen el trabajo
  • Cambios de producto que necesitan UX humano

Cron job vs agentic loop

⏰

Cron job

Ejecuta algo a una hora fija. Paralelo, sin dependencias entre tareas.

# Lunes 9am: tarea A, B, C en paralelo
0 9 * * 1  run-task-A
0 9 * * 1  run-task-B
0 9 * * 1  run-task-C
🔁

Agentic loop

Ejecuta algo cuando el paso anterior terminó bien. Secuencial, con estado.

# tarea A → B (depende de A) → C (depende de B)
A() && B() && C()
# El loop respeta el ORDEN LÓGICO del trabajo

2El motor: RemoteTrigger

El tool de Claude Code que permite disparar una nueva sesión desde dentro de una sesión existente. Es el mecanismo técnico que hace posibles los agentic loops.

Cómo funciona
El prompt es todo
vs /schedule

Cuando Claude llama a RemoteTrigger:

  1. Claude Code registra el trigger con el prompt indicado
  2. La sesión actual continúa hasta terminar normalmente
  3. Una vez finalizada, el sistema lanza una nueva sesión independiente
  4. La nueva sesión no tiene acceso al historial de la anterior
RemoteTrigger(
  prompt: "Ejecutá el issue #43 siguiendo complete-issue.
            Contexto: venís de completar el #42.
            [loop_count=2/5]"
)

Como las sesiones no comparten contexto, el prompt es el único canal directo.

✗ Prompt pobre

"ejecuta el siguiente issue"

La sesión nueva no sabe qué hacer ni de dónde viene.

✓ Prompt rico

"Ejecutá #43 autónomo.
Venís de completar #42 (F4-016).
Fase 4, Sprint 15.
Verificá condiciones de
parada antes de iniciar."
RemoteTrigger/schedule
Cuándo dispara Cuando la sesión termina En un horario fijo (cron)
Dependencia Depende del resultado anterior Independiente
Caso de uso Pipelines secuenciales con estado Tareas periódicas sin dependencias
Ejemplo issue #42 → #43 → #44 Revisar estado cada lunes
Nota práctica: En Amauta la implementación final reemplazó RemoteTrigger por un mecanismo agnóstico: la sesión escribe next-prompt.md y un script local (loop-runner.sh) levanta la siguiente. Esto independiza el loop de Claude Code específicamente.

3El patrón de handoff

El traspaso de responsabilidad entre sesiones. Como el contexto de conversación no persiste, todo lo necesario debe vivir afuera.

Qué persiste — qué no

✗NO persiste✓SÍ persiste
Historial del chatArchivos en disco
Variables en memoriaCommits en Git
Resultados de tools previosIssues en GitHub
Decisiones tomadas en sesiónDocumentación actualizada
Errores que ocurrieronCLAUDE.md y archivos de estado

Los tres canales de estado

🐙

GitHub

El más confiable. Un issue abierto/cerrado es verdad objetiva verificable con gh issue view.

📄

Archivos

CLAUDE.md, roadmap.md, loop-status.md actúan como memoria compartida.

📜

Commits

El historial de Git es la bitácora. git log --oneline -5 te dice qué hizo la sesión anterior.

Anti-patrón: el handoff frágil

✗ MAL

  • "continúa desde donde estabas"
  • "recordás lo que hablamos antes?"
  • "el issue que dijiste que ibas a hacer"

Ese contexto murió con la sesión anterior. La nueva es una pizarra en blanco.

✓ BIEN

  • "ejecutá #82 (F4-017) verificando que #81 está cerrado"
  • "leé CLAUDE.md y determiná el siguiente issue"
  • "el roadmap dice que el siguiente es F4-017"

Cada instrucción es verificable desde estado externo.

4Condiciones de parada

Un loop sin condiciones de parada es un loop infinito. No son opcionales — son la diferencia entre automatización profesional y caos.

💼

Negocio

¿Hay issues abiertos en el sprint actual? Si no, stop limpio y resumen.

⚡

Recursos

¿Contexto > 85%? ¿Quota mensual > 95%? No disparar nueva sesión.

🚨

Error

¿Tests fallaron? ¿Compilación rota? ¿Issue ya completado dos veces? STOP con alerta.

Counter de sesiones: mecanismo simple y efectivo. Pasá [loop_count=3/10] en el prompt. Cuando llega al límite → stop, sin importar si hay más issues. Es el guardrail de último recurso.

5Los 5 guardrails profesionales

Los mecanismos que convierten un loop experimental en automatización de producción.

Guardrail 01

Quota de contexto de sesión

Si la sesión leyó >15 archivos, ejecutó >20 comandos o tiene >30 turnos → no disparar. La calidad del razonamiento degrada con contexto saturado.

Guardrail 02

Límite de sesiones por loop

Counter en el prompt: [loop_count=X/N]. Recomendado: 3 para testing, 5-8 estable, 10 máximo. Evita vaciar la quota mensual en una noche.

Guardrail 03

Detección de loop sin progreso

¿El último issue cerrado es el mismo que el que va a ejecutarse? → loop detectado, STOP. Anti-bug crítico contra ciclos vacíos.

Guardrail 04

Log de auditoría

loop-status.md con timestamp, sesión, issue, resultado, razón de parada. Sin esto no podés saber por qué el loop terminó.

Guardrail 05

Tercera skill: auditoría

Cada N issues, una sesión revisa tests completos, tipos TypeScript y coherencia arquitectónica. Interviene entre ciclos, no en cada uno.

Checklist

Antes de habilitar autónomo

✓ Counter definido · ✓ Stop por "sin issues" · ✓ Heurística contexto · ✓ Log auditoría · ✓ Detección sin progreso · ✓ Arranque manual documentado.

6Implementación por fases

Activar el loop completo desde el día 1 es la forma más rápida de descubrir problemas caros. Lo más simple que puede funcionar, antes de agregar más.

Fase 0 · Verificación manual

✓ Completada · 2026-03-29

Ejecutar project-manager y complete-issue manualmente. 3 issues distintos sin sorpresas. Sin esto, automatizar es ciego.

Fase 1 · Loop mínimo (1 issue, 2 sesiones)

✓ Completada · 2026-03-29

Probar el handoff: project-manager → complete-issue → STOP. El primer handoff real entre sesiones independientes.

Fase 2 · Loop bidireccional (2 issues, 4 sesiones)

✓ Completada · 2026-03-29

Ciclo completo de ida y vuelta. PM → CI → PM → CI → STOP. Counter se propaga: 0/2 → 1/2 → 1/2 → 2/2.

Fase 3 · Loop con guardrails activos (5-8 issues)

⏳ Pendiente

Todos los guardrails activos. Pruebas: parada natural, parada por counter, log fiel.

Fase 4 · Tercera skill (auditoría periódica)

⏳ Pendiente

Cada 3 issues, una sesión de auditor revisa tests + tipos + documentación. Si encuentra problemas → STOP.

Fase 5 · Modo producción

⏳ Pendiente

Sin supervisión, notifica cuando para, output auditable. Requiere 10+ issues exitosos y guardrails probados en todas las condiciones.

Regla de oro: No avances a la siguiente fase hasta que la anterior funcione sin sorpresas. Una sorpresa en Fase 1 cuesta 2 sesiones perdidas. La misma sorpresa en Fase 5 puede ser 50.

#!/bin/bash
# loop-runner.sh
NEXT_PROMPT="docs/ai-skills/automata-dev/next-prompt.md"

while [[ -f "$NEXT_PROMPT" ]]; do
  PROMPT=$(cat "$NEXT_PROMPT")
  rm "$NEXT_PROMPT"
  echo "$PROMPT" | claude --print --dangerously-skip-permissions
done

echo "Loop terminado."
# loop-runner.ps1
$NextPrompt = "docs/ai-skills/automata-dev/next-prompt.md"

while (Test-Path $NextPrompt) {
  $Prompt = Get-Content $NextPrompt -Raw
  Remove-Item $NextPrompt
  $Prompt | claude --print --dangerously-skip-permissions
}

Write-Host "Loop terminado."

Pregunta 1

Una sesión nueva arranca después de un RemoteTrigger. ¿Qué le pasaría si le dijeras: "continuá desde donde estabas"?
Continuaría sin problema, las sesiones comparten contexto
No tendría idea — el contexto de la sesión previa no persiste
Leería el historial automáticamente
Correcto. Entre sesión y sesión solo persiste el estado externo: archivos, commits, issues. El historial de chat muere. Por eso el prompt de handoff debe ser autocontenido.

Pregunta 2

¿Cuál de estos NO es un guardrail recomendado?
Counter de sesiones [loop_count=X/N]
Heurística de contexto saturado
Reintentar automáticamente cuando los tests fallan
Detección de loop sin progreso (mismo issue dos veces)
Correcto. Reintentar tests fallidos automáticamente esconde problemas reales y consume quota. El patrón correcto es STOP, no cerrar el issue, reportar el problema.

Pregunta 3

¿En qué fase recién deberías probar que el loop bidireccional funciona (4 sesiones)?
Fase 0 — verificación manual
Fase 1 — loop mínimo (1 issue)
Fase 2 — loop bidireccional (2 issues)
Fase 5 — modo producción
Correcto. Fase 2 es exactamente eso: PM → CI → PM → CI → STOP. Verifica que el counter se propaga y que la segunda sesión de project-manager puede determinar el estado sin ver el historial de la primera.
